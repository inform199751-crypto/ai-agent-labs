# Lab 1｜工具 schema 體檢

受測系統：微醺之夜 Bistro（`bistro_concierge`）

---

## 這一關在問什麼

模型決定要不要呼叫一個工具，唯一的依據是那個工具的文字描述。
它看不到原始碼、問不到同事。描述寫不好，結果不是「用錯」，
而是**在該用的時候根本沒想到它**——而這種失敗不會報錯，只會看起來像模型比較笨。

同時，每個工具的定義都常駐在對話裡，每次呼叫都要付一次。**描述是稅。**

所以要回答：**這些描述夠不夠模型判斷？代價是多少？**

---

## 我量到什麼

### 先講一個前提：這關是翻譯，不是抽取

Bistro 是 Dify workflow，**沒有現成的 function-calling schema**。
它的「工具」是四個 parameter-extractor 節點接 HTTP 或 code 節點，
路由由 question-classifier 決定。

所以我做的是翻譯。翻譯規則訂得很保守，避免把自己的文筆當成系統的成績：

- **參數描述逐字搬，一個字沒改**（來源：`src/build_dsl.py`）
- **工具層描述用 Dify 節點的原始 `instruction`**，不潤飾
- 只加了 `enum`（Dify 沒這個欄位，但描述裡本來就列了那些值）

### 結果

```bash
PYTHONIOENCODING=utf-8 python course-scripts/lab1_schema_lint.py bistro_tools.json --tools 5 --turns 30 --tasks 60
```

| 工具 | 結果 | schema |
|---|---|---|
| `manage_reservation` | ✗ 沒寫「何時用」 | 407 tokens |
| `quote_bill` | ✗ 沒寫「何時用」 | 215 |
| `report_complaint` | ✓ 通過 | 405 |
| `query_ops_metric` | ✗ 沒寫「何時用」 | 154 |

**參數那一關四支全過，0 錯誤 0 警告。**

---

## 判斷一：那三個錯誤是誤報

Dify 的路由由 question-classifier 決定，觸發條件寫在它的 class 名稱裡：

```
訂位:查詢空位、訂位、改期、取消
價格試算:問價錢、算多少錢、低消與服務費
客訴:抱怨、不滿、餐點有問題、要求補償
店內營運數據:成本、毛利、營收、庫存、排班(僅限店內人員)
```

**資訊存在，只是存在別的地方。** 這是架構差異，不是漏寫。

### 但這個判定有實際後果

如果哪天要把 Bistro 從 Dify 搬到 function-calling agent，
**這三支會直接壞掉**——模型拿不到任何觸發線索，而 classifier 節點不會跟著搬過去。

所以正確的說法不是「這不是問題」，是：
**「在現有架構下不是問題，但它是一筆遷移債。」**

---

## 判斷二：那支「通過」的，其實沒通過

`report_complaint` 被判合格。我去看為什麼——

它的 L3 定義裡有「**要求**賠償退費免單」，`要求` 命中了 linter 的關鍵字表。
**不是因為真的寫了觸發情境。**

這是假陽性。工具用字串比對判斷「有沒有寫何時用」，
而中文裡「要求」出現在任何語境都會命中。

> 這一題的價值不在扣分，在於：**通過一個檢查不等於滿足那個檢查想保證的東西。**
> 如果我只看 3 ✗ 1 ✓ 就下結論，會得到一個錯的結論——
> 而且是往樂觀方向錯，那比悲觀方向錯危險。

---

## 判斷三：我不建議把那三個「修好」

修的方法很簡單：把 classifier 的分類文字折回每支工具的描述。
我做了一版（`bistro_tools_v2.json`），四支全過。

**代價是每支從 295 漲到 396 tokens（+34%）。**

而這筆錢買不到任何東西：

- Dify 的路由**不讀工具描述**，classifier 讀完就決定了，描述寫再好也不影響路由
- 分類文字在 classifier 節點裡**一輪只付一次**；折進工具描述後變成**每次呼叫都常駐**

所以現狀在成本上是對的。**該留著這筆遷移債，直到真的要遷移。**

`bistro_tools_v2.json` 保留在 repo 裡，當作遷移時的現成材料——
不是當作「修正版」。

## 互評四問（S36、S76）我自己的答案

**Q：模型什麼時候會想到用它？**

現有架構下這題問錯對象了——該問的是 classifier，不是工具。
classifier 的五個 class 名稱互斥且涵蓋完整，
唯一的灰色地帶是「同時有抱怨和其他需求」，
而那個 instruction 已經明文處理：歸到客訴，但回覆時要一併回答另一個需求。

**Q：這個工具真的要停在第 6 階嗎？（足跡階梯 S31）**

`quote_bill` 不用。它是純計算，Dify 的 code 節點就做得到，
所以實際實作**確實**是 code 節點而不是 HTTP 呼叫——
理由是 Dify 的 code sandbox 沒有網路，但純計算不需要網路，
**API 掛掉帳單照樣算**。

`manage_reservation` 必須走 HTTP，因為它要存狀態（SQLite）。
這個分界是刻意的，不是隨便決定的。

## 後續：加了新參數之後

這次稽核之後，我在系統裡加了一個 `detail` 參數
（排班查詢預設回摘要，要明細才帶這個旗標）。
順手用同一把尺量新的描述（`bistro_tools_v3.json`）：

```
query_ops_metric   0 錯誤 0 警告   250 → 363 tokens
```

乾淨過關，但那支工具漲了 **45%**。

這是一個很具體的取捨實例：新增一個參數要付出的不只是實作時間，
還有**每次呼叫都要付的常駐成本**。
`detail` 的描述我寫得比較長（要教模型分辨「完整班表」和「這週怎麼排」），
那個長度直接換算成錢。值不值得看使用頻率——
如果店長很少要完整班表，這 113 tokens 幾乎每次都白付。

## 代價與限制

**一、這關量的是翻譯品質，不完全是系統品質。**
工具層描述是 Dify 的 instruction 原文，參數描述是原作者寫的。
翻譯的邊界（要不要加 enum、要不要調整 required）是我決定的，
會影響結果。我選了最保守的做法，但它不是唯一的做法。

**二、token 數是本地估算**，不同 tokenizer 可差 ±20%。

**三、`required` 欄位我照抄了 Dify 的設定**（幾乎全是 `false`）。
在真正的 function-calling schema 裡，`action` 應該是必填。
照抄是為了忠實，但這代表 v1 那份不能直接拿去用。
