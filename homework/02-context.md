# Lab 2｜Context 預算

受測系統：微醺之夜 Bistro（`bistro_concierge`，約 7,400 行 Python，Dify workflow + 標準函式庫 HTTP API）

---

## 這一關在問什麼

模型的對話視窗是固定大小的。系統提示、工具定義、記憶這些東西一開場就佔掉一部分，
剩下的才輪得到對話本身。塞滿之後系統會自動壓縮舊訊息——而壓縮會丟東西。

所以要回答三個問題：**現在還剩多少能放對話？什麼時候會被壓縮？壓縮時什麼絕對不能丟？**

---

**實際視窗需向 provider 文件核對**——這是假設不是量測，下面所有推算都繼承這個假設。

### 算出來的結果

常駐 = 3,126（系統提示）。Dify 的工具 schema 不常駐在回答的 LLM 節點裡，
所以這裡是 0，不是 1,584——**這是架構差異，不是我少算**。

```
常駐 3,126 只佔視窗的 2.4%
壓縮門檻 50% → 觸發點 64,000 → 可放對話 60,874
```

| 情境 | 每輪成長 | 幾輪後觸發壓縮 |
|---|---|---|
| 對客（帳單試算） | 430 | **141 輪** |
| 店內（查庫存） | 985 | **61 輪** |
| 店內（要完整班表） | 4,066 | **14 輪** |

## 判斷一：壓縮門檻設 50%

課程的討論題是「門檻改成別的會怎樣」。三個選項的實際差距：

| 門檻 | 觸發點 | 可放對話 | 對客能撐幾輪 |
|---|---|---|---|
| 35% | 44,800 | 41,674 | 96 |
| **50%** | 64,000 | 60,874 | **141** |
| 70% | 89,600 | 86,474 | 201 |

**我選 50%，但理由不是「怕爆」。**

先看實際使用場景：餐廳的對客對話是訂位、問菜單、算帳，
一次三到八輪就結束，不會有人跟客服機器人聊 141 輪。
店長查營運數據一次三到五輪。**最極端的情境（連續要完整班表）也才 14 輪。**

也就是說，**這個系統在任何合理的使用模式下都碰不到壓縮門檻**。

所以真正的問題變成：既然碰不到，為什麼不調高到 70% 換更多空間？

因為**調高沒有換到任何東西**。空間本來就用不完，多給 25,600 tokens 是多給用不到的東西。
而調高會付出代價：門檻以上的餘裕從 64,000 縮到 38,400，
那塊空間是留給「壓縮動作本身的輸出」和「下一輪的工具輸出」的。
如果哪天使用模式真的變了、而我調高了門檻，那次壓縮可能來不及。

**所以 50% 是「保守的預設在這裡零成本」，不是「我算出 50% 最佳」。**
如果哪天真的碰到門檻，那代表使用模式改變了——
該做的是回來重算，不是把門檻往上調。

### 這個判斷的前提

**上面整段推理只在「工具輸出受控」的前提下成立。**

而我在量測時發現前提差點不成立：排班明細一次吐 3,806 tokens，
是第二名的五倍。它之所以沒出現在原本的計算裡，
是因為那個端點壞掉了——**bug 掩蓋了一個真的 context 問題**。

修好之後我把它改成預設回摘要（563 tokens），最大的常規工具輸出才回到庫存的 725。
但完整明細那條路徑**現在是可達的**，防線只剩「參數擷取器會不會正確分辨
『完整班表』和『這週怎麼排』」——那是提示詞層的防線，有機率性失誤。

這正是課程 S49 那句話的實例：**撐爆視窗的幾乎永遠是工具輸出。**
我原本以為架構選擇（Dify 不常駐 schema）省了 1,584 tokens 是優勢，
實際算下來只值四輪（141 vs 137）。**真正的變數從頭到尾都是工具輸出。**

## 判斷二：雙層門檻 85% / 50%

閘道層 85%、agent 層 50%，拉開 35 個百分點。

課程的規則是不能太近，否則會震盪：agent 壓縮完落在閘道門檻附近，
每一輪都被再壓一次。35 個百分點遠超過建議的 20，不會互相觸發。

**外層是保險絲，不是第二個常規機制。** 以這個系統的用量，
外層永遠不該被觸發——如果它被觸發了，那本身就是一個該去查的異常訊號。

## 判斷三：尾巴策略——課程推薦的那個，我不能選

課程給兩個選項：

| 策略 | 保留量 | 課程實測召回率 |
|---|---|---|
| Legacy 大尾巴 | 12,800（觸發點 × 20%） | 45.8% |
| Lean 小尾巴 | 10,000（視窗 × 2.5%，夾在 10K–25K） | **68.3%**，且只用 0.3 倍 token |

數字上 Lean 完勝，看起來應該選 Lean。

**但我不能選。**

Lean 的 68.3% 是**搭配回溯搜尋**測出來的——小尾巴只留最近的，
丟掉的部分靠事後搜尋找回來。沒有回溯搜尋的話，丟掉就是真的丟掉。

而 Bistro 是 Dify workflow，**沒有 session 回溯搜尋這個機制**。
節點之間傳遞的是變數，不是可檢索的對話歷史。

所以這個系統的實際處境是：

- 選 Lean → 拿到小尾巴的成本優勢，但拿不到那 68.3%，因為前提不成立
- 選 Legacy → 多留 2,800 tokens，留的是「最近」不是「最重要」

兩個都不好。**但這個系統碰不到門檻，所以這個選擇目前不影響任何事。**

真正的結論是：**如果哪天使用模式改變、真的會觸發壓縮，
該做的第一件事不是挑尾巴策略，是先把回溯搜尋補起來**——
不然兩個選項都是在輸的那一邊做選擇。

> 這一段是我覺得這次作業最有價值的地方：
> 課程給的建議有一個沒寫在標題上的前提，而我的系統不滿足它。
> 照抄「選 Lean」會得到一個看起來正確、實際上前提不成立的答案。

## 第 4 題：哪些識別碼絕對不能被改寫

課程要三種，我找到四種。

先驗證問題真的存在。我用真實格式寫了一段訂位→改期→客訴的對話
（`bistro_conversation.txt`），跑內建規則：

```
抓到 7 個：金額 5 個、日期 2 個
```

漏掉的：

| 識別碼 | 範例 | 被改寫的後果 |
|---|---|---|
| **訂位代碼** | `R7F3A91` | 變成「某筆訂位」→ 客人改不了期、取消不了 |
| **客訴單號** | `C20260926-205012-0007` | 變成「那次客訴」→ 追蹤斷線，店長對不起來 |
| **電話** | `0912-345-678` | 訂位唯一的聯絡方式，沒了就找不到人 |
| **桌號** | `T01` | 外場過不去，「那桌」在尖峰時段沒有意義 |

**金額被摘要成「一千多塊」還能重算；訂位代碼被摘要成「某筆訂位」就結束了。**
`docs/API規格.md` 裡 `cancel` 和 `reschedule` 都以 `code` 為必填——
代碼消失等於那筆訂位進入無法操作的狀態。

四條 regex 都對得上原始碼裡的產生器，不是猜的格式：

| 識別碼 | regex | 出處 |
|---|---|---|
| 訂位代碼 | `\bR[0-9A-F]{6}\b` | `reservation._new_code()` = `"R" + token_hex(3).upper()` |
| 客訴單號 | `\bC\d{8}-\d{6}-\d{4}\b` | `api._next_ticket()` = `C%Y%m%d-%H%M%S-0001` |
| 電話 | `\b09\d{2}-?\d{3}-?\d{3}\b` | 訂位表單欄位 |
| 桌號 | `\bT\d{2}\b` | `tables.yaml` |

補上後 **7 → 11**。

作答在 `bistro_patterns.py`，用 import 擴充課程腳本，**沒有修改原檔**——
這樣課程材料保持乾淨，而且我的擴充是獨立可檢視的一個檔案。

## 代價與限制

**一、視窗大小是假設。** 128K 來自課程預設。DSL 設的是 `gpt-5`，
實際視窗要查 provider 文件。整份推算繼承這個假設，如果實際視窗不同，
輪數會等比例變化，但「碰不到門檻」的結論在視窗更大時只會更成立。

**二、token 數是本地估算不是 provider 實測。** 用的是 CJK 1.3 tokens/字的粗估。
課程自己標了不同 tokenizer 可差 ±20%。真正的數字只有 provider 回報的 usage 知道。
這裡所有數字都是 MODELED 不是 OBSERVED。

**三、每輪成長是組合估計。** 430 = 客人訊息 40 + 分類 10 + 參數擷取 60 + 工具輸出 167 + 回覆 150。
前後那幾項是估的，只有工具輸出是實測。工具輸出佔大頭，所以誤差主要來自小項。

**四、「碰不到門檻」是基於我對使用模式的判斷，不是流量資料。**
這個系統還沒有正式上線的對話紀錄。如果真實使用跟我想的不一樣
（例如店長習慣在同一個對話裡連續查一整輪營運數據），14 輪那條路徑會比我預期的更常走到。
