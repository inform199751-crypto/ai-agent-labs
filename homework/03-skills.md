# Lab 3｜SKILL.md Linter

受測對象：**兩批公開的真實 skill 語料**（不是受測系統，理由見下）

---

## 這一關在問什麼

SKILL.md 是寫給 agent 看的操作手冊。課程主張寫作標準應該可以被 CI 檢查，
並給了一支 linter：八條規則，離開碼 0 通過、1 有錯誤，可以直接掛進 CI。

要回答的是：**這些規則真的能分辨好壞嗎？**

---

## 先講一個問題：我沒有素材

Bistro 沒有 SKILL.md。`.claude/` 裡只有一個 `launch.json`。

所以我改用兩批公開的真實語料：

- 一套廣泛使用的 agent skill 集：**14 支**
- Dify 專案自己寫的 skill：**5 支**

這代表**這一關檢驗的是工具，不是我的系統**。
這是限制，但也讓這關變成五關裡唯一能拿「業界基準」當對照的一關。

---

## 我量到什麼

```bash
PYTHONIOENCODING=utf-8 python course-scripts/lab3_skill_lint.py <skill 目錄>/SKILL.md
```

**19 支全部不及格，零支通過**（每支 3～7 個錯誤）。

當一個 linter 在公認品質不錯的語料上 100% 噴錯，
要先懷疑的是規則，不是語料。所以我去統計是哪些規則在噴：

| 規則 | 命中 | 我的分類 |
|---|---|---|
| `description` 超過 60 字元 | **19 / 19** | 模板一致性 |
| 缺 `## Pitfalls` | **19 / 19** | 模板一致性 |
| 缺其他必要章節 | 33 次 | 模板一致性 |
| 缺 `## Verification` | 17 / 19 | 模板一致性 |
| 沒有 `author` 欄位（警告） | 19 / 19 | 模板一致性 |
| 開頭沒講「不做什麼」（警告） | 18 / 19 | 模板一致性 |
| 用了 shell 指令名 | 7 / 19 | 看似有鑑別力 |
| 高風險步驟寫成高自由度 | 3 / 19 | 有鑑別力 |
| `description` 沒寫何時用 | **1 / 19** | 有鑑別力 |

## 判斷一：60 字元上限是用中文校準的

工具自帶的「好例子」通過檢查，它的 description 是**中文 37 字**：

> 掃描原始碼與 log 中的個資並依規則遮罩。處理個資、PII 外洩時使用。

做什麼＋何時用兩段齊全，37 字綽綽有餘。

19 支英文語料的長度分布：

```
最短  79  ← 已經超過上限 32%
中位 154
最長 335
≤60 的：0 / 19
```

**英文 60 字元大概只夠寫一個子句。**

同一個語意量，中文的字數天生比英文少一半以上。
這條規則不是錯，是**沒翻譯**——它在中文語境下是合理的，套到英文語料就變成全員死刑。

> 這一題我覺得是整份作業裡最乾淨的一個發現：
> 一條看起來客觀的量化規則，隱含了一個沒寫出來的語言假設。

---

## 判斷二：章節檢查測的是「有沒有照抄模板」

工具硬寫死四個必要章節：`When to Use` / `Procedure` / `Pitfalls` / `Verification`。

19 支沒有一支完全照用。但它們**不是沒寫陷阱**——
是標題叫別的名字，或者把陷阱寫進正文而不是獨立章節。

這條規則測的是模板一致性，不是內容品質。
在一個團隊內部強制統一格式是合理的；
拿來評斷外部語料的好壞，測到的東西和宣稱的東西不一樣。

---

## 判斷三：那條「看似有鑑別力」的，誤報又漏報

「用了 shell 指令名」只噴 7/19，看起來是真的在分辨什麼。
這條規則的立論很強（課程 S72）：
**你在 SKILL.md 裡寫什麼動詞，agent 就做什麼動作**——
寫 `grep` 它就去開 shell，寫原生工具名它才會用結構化的那個。

我逐一回原文看那 7 次命中。**全部是英文單字，沒有一個是 shell 指令**：

```
"agents find and apply effective approaches"    ← find 是動詞
"head-to-head wording tests"                    ← head 是慣用語
"the head the previous review saw"              ← head 是名詞
```

規則的 pattern 是 `\bfind\b` 和 `\b(?:cat|head|tail)\b`，
在英文散文裡這些是高頻常用字。

### 而且它漏掉了唯一真的那個

整批語料裡唯一一行貨真價實的 shell pipeline，三個指令全中：

```bash
BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | awk '{print $1}')
```

**工具沒抓到。** 因為它會先把 ``` 圍起來的程式碼區塊整段刪掉再比對。

排除程式碼區塊本身是合理設計（不然沒辦法示範指令）。
但**程式碼區塊正是 agent 讀取動作的地方**——
一支 SKILL.md 叫 agent 去跑那行 pipeline，就是 S72 在警告的事，
不會因為它包在反引號裡就不算。

**這個排除把規則自己的立論挖掉了。**

---

## 判斷四：唯一站得住的那條

「`description` 沒寫何時用」只噴 **1 / 19**。

這是整組規則裡最重要的一條——它決定模型會不會在對的時機打開這本 skill，
跟 Lab 1 查的是同一件事。

**19 支真實 skill 裡 18 支都做對了。**

所以完整的結論是：
**語料在真正要緊的地方是強的，「全員不及格」幾乎全部來自標題取名和字數。**

## 互評四問（S76）我自己的答案

工具在每次執行後都會印這四問。我拿它們回頭問這個 linter 本身：

**Q1：使用者說哪句話時，模型會打開這一本？**
這支 linter 的定位很清楚——「我要檢查 SKILL.md」。沒有歧義。

**Q2：有沒有「做錯會很慘」的步驟被寫成高自由度？**
有，而且是它自己。離開碼 1 代表「有錯誤」，
而它對 19 支業界語料全部回 1。**照原樣掛進 CI，第一天就會把整個 repo 擋下來**，
而擋下來的理由 90% 是格式。這個後果很慘，但規則本身沒有任何分級機制。

**Q3：有沒有用 shell 指令名稱取代原生工具？**
判斷三整段就是在答這題——它有這條規則，但實作誤報又漏報。

**Q4：Verification 段落，agent 真的執行得了嗎？**
它要求別人有 `## Verification`，自己的驗證方式是「離開碼」。
離開碼是可執行的，這一點它做到了。

## 如果要真的掛進 CI，我會怎麼調

| 處置 | 規則 |
|---|---|
| **留** | `description` 沒寫何時用、高風險步驟的自由度、description 寫實作細節 |
| **改參數** | 字數上限分中英文（英文建議 ≥150）；章節名稱改語意比對，不做字面比對 |
| **拿掉或重寫** | 原生工具名——pattern 要收緊到「後面接路徑或參數」才算；<br>而且不該排除程式碼區塊，否則漏掉真正該抓的 |

---

## 代價與限制

**一、這關的語料不是受測系統。** Bistro 沒有 SKILL.md，
所以這一關的結論是關於工具的，不能拿來評價我的系統。

**二、我沒有逐字讀完 19 支 SKILL.md。**
規則命中率是程式統計的；「7 次命中全是英文單字」那個結論，
我是逐一回原文檢查過的；但「它們不是沒寫陷阱，是標題叫別的名字」
這個判斷是抽樣看的，不是全數確認。

**三、語料的選擇會影響結論。**
兩批都是英文語料。如果拿中文寫的 skill 來跑，
60 字元那條規則的命中率會完全不同——而這正好是判斷一的論點，
所以這個限制同時也是佐證。
