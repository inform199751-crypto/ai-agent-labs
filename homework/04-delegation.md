# Lab 4｜委派計畫成本試算

受測系統：微醺之夜 Bistro（`bistro_concierge`）

---

## 這一關在問什麼

把一個任務丟給子代理，直覺上像開一條執行緒——多一個人做事，比較快。

但子代理不是執行緒。它會帶著一整份系統提示和工具定義啟動，
那是固定成本，開一個付一次。所以委派買的不是速度，是 **context 隔離**：
子代理在自己的空間裡翻了一萬個 token 的資料，父層只付它回傳的那兩百個。

要回答的是：**哪些任務值得這樣拆？拆了之後有哪些坑？**

---

## 先講一個前提：這關是設計提案，不是現況稽核

**Bistro 目前零子代理。** 全部是 deterministic Python 加 Dify workflow 的固定路由。

所以我做的是：把 `src/` 裡六個真實工作負載，
當成「如果改用多代理重建」的計畫草案來評估。

這代表過程／結論比是我依各模組實際行為估的，**不是執行期量測**。
每個任務我都在 `bistro_plan.json` 留了 `_basis` 欄位記錄數字怎麼來的。

---

## 我量到什麼

### 固定成本我用實測值，不用預設值

課程預設子代理固定成本 15,000 tokens。我用 Bistro 的實際數字：

```
系統提示（對客）      3,126   讀 prompts/build/system_guest.md
工具 schema（4 支）   1,584   Lab 1 的翻譯版加總
                    ─────
固定成本              4,710   ← 只有課程預設的 31%
```

提示詞比課程基準省三分之二，因為它是從 `knowledge/*.yaml` build 出來的，沒有贅肉。

### 六項判定

```bash
PYTHONIOENCODING=utf-8 python course-scripts/lab4_delegate_cost.py bistro_plan.json
```

| # | 工作負載 | 過程 | 結論 | 比 | 判定 |
|---|---|---|---|---|---|
| 1 | 每日食材價格監控 | 55,000 | 150 | 367:1 | ✓ 拆 |
| 2 | 評論六面向分析 | 35,000 | 300 | 117:1 | ✓ 拆 |
| 3 | 貼文生成→審核迴圈 | 18,000 | 400 | 45:1 | ✓ 拆 |
| 4 | 貼文發布硬閘門 | 4,500 | 120 | 38:1 | ✓ 拆 |
| 5 | 貼文排程與發布 | 2,500 | 250 | 10:1 | ! 可拆 |
| 6 | L3 客訴即時通報 | 900 | 700 | **1:1** | ✗ 不要拆 |

```
父層省下的 context： 113,980
多付的固定成本：      28,260（6 × 4,710）
淨效果：             省 85,720
```

## 判斷一：我原本猜錯的那一項

開始跑之前，我以為「L3 客訴即時通報店長」是典型的該拆案例——
它要判等級、要寫紀錄、要發通知，聽起來就是一串該丟出去的雜事。

**跑完是明確不該拆，過程／結論比只有 1:1。**

原因在 `docs/API規格.md` 裡就寫著了：

> `message` 的內容就是要對客人講的話，LLM 節點只需要用自己的語氣轉述

**回傳的東西幾乎要原封不動講給客人聽，所以結論跟過程一樣大。**
委派它只是把 context 從一個地方搬到另一個地方，還多付一份 4,710 的固定成本。

> 這一題我把自己的錯誤判斷寫進來，是因為它示範了這個工具的用途：
> 直覺會被「這件事聽起來很雜」誤導，比值不會。

---

## 判斷二：工具點名的兩個「坑」，系統早就繞開了

| 工具的指控 | 系統實際的做法 |
|---|---|
| **第 1 項**「必須活過重啟 → 你需要的是排程不是委派」 | **它已經是排程。** 掛在 Windows Task Scheduler，理由寫在啟動檔註解：政府 API 一次只回最近四天，**漏掉一天永久補不回來** |
| **第 5 項**「啟動背景行程卻不等它」＋「必須活過重啟」 | 用**佇列＋發布前一刻重審**。原始碼註解的理由比工具的更深一層：「佇列只記草稿，不記已核准這個狀態。**規則是活的，核准不是。**」 |

工具問的是「如果這台機器現在重開機，這件事還會發生嗎？」
兩個工作負載的答案都是「會」，因為它們本來就沒用委派去做這件事。

**這兩項是誤報。而且是好消息**——它代表「委派 vs 排程 vs 佇列」的分界，
這個系統在兩個月前就分對了，理由還寫在原始碼裡，不是事後補的。

---

## 判斷三：工具自己的盲點

第 4 項「貼文發布硬閘門」比值 38:1，工具判「該拆」。

但它是**純規則比對**——載入三份 yaml（禁語、酒責、語氣），
逐條檢查草稿。不需要 LLM，更不需要一個代理。**寫成 function 就好。**

高過程／結論比只說明「值得隔離 context」，
沒說明「需要一個代理」。這兩件事不一樣。

### 還有一個設計選擇要講明

工具的單項判定函式**完全不讀固定成本**，只看比值。
固定成本只影響總帳。

所以我把固定成本從 4,710 換成預設的 15,000 再跑一次：

```
淨效果：省 23,980（仍然划算）
```

總帳的結論不翻盤，但**單項判定一個字都沒變**——
因為它根本沒把固定成本算進去。

這不是 bug，是設計選擇。但寫結論時不能假裝它有考慮，
否則會以為「拆」這個判定已經含了成本效益，其實沒有。

---

## 判斷四：先收斂再展開

課程另一個模式：目標很多但命中很少時，不要全面展開。

Bistro 有一個現成的例子。`price_watch.py` 監控的政府 API 涵蓋**近千種作物**，
但 `recipes.yaml` 的 `open_market` 食材只有 **12 項**：

```bash
PYTHONIOENCODING=utf-8 python course-scripts/lab4_delegate_cost.py --scan-first 1000 12
```

```
A 全面展開    1000 × 15,000                = 15,000,000
B 先掃描再展開 2,015,000（掃描）＋ 12 × 15,000 =  2,195,000
→ B 省 85%
```

而 `price_watch.py` **已經是 B**：監控清單直接從 `recipes.yaml` 產生，
菜單換了監控範圍自動跟著換，不用維護第二份清單。

## 其他檢查項

**輸出契約（S81）**：第 5 項沒有 `output_schema`——這是我在草案裡故意留的。
沒有契約，子代理回的是散文，父層要再花一次 LLM 呼叫去解析它。

**回報分組（S80）**：我把 1 分在 `daily`、2 分在 `weekly`、3-5 分在 `marketing`、
6 不分組。同組一起回報，讓「三個行銷任務一起看」
和「每日監控自己完成自己回」不會互相等待。

**迭代預算（S80）**：父層上限 500 ＋ 6 個子代理 × 50 = **總共可能跑到 800 次**。
「我設了上限」不等於「總成本有上限」——預算監控要看總和，不是看單項。

---

## 代價與限制

**一、這關是設計提案。** 系統目前零子代理，六項的過程／結論比是依模組實際行為估的，
不是執行期量測。估錯的話判定會跟著錯，特別是第 5 項（10:1）落在邊緣，
估值稍微偏一點就會跨過「可拆／不要拆」的界線。

**二、固定成本假設整套提示詞都搬過去。**
實際上子代理應該只帶它需要的工具，固定成本會更低，
那會讓「拆」更划算。所以 4,710 是保守估計。

**三、我沒有實作任何一個子代理。**
這份計畫的結論是「哪些值得拆」，不是「拆完會更快」。
速度沒有被量測過，也不是這個工具在量的東西。
