## Part A 第 1 題：三句斷言，對應三個軸

我先照直覺寫一版，再改寫。兩版都丟進工具判定。

### 第一版（直覺寫法）→ 3/3 是變更偵測器

```python
# U1 訊息序列
assert resp["message"].startswith("很抱歉,2026-08-17 是週一")
# U3 成本／快取
assert quote["total"] == 1188
# U7 安全邊界
assert ops_resp["message"] == "授權碼不正確,無法查詢營運數據。"
```

三句都在凍結當下的值。改一個字、調一個算法就全紅，
而系統的行為完全沒變。

### 第二版（改寫成關係）→ 0/3

| 軸 | 契約 | 為什麼是關係不是值 |
|---|---|---|
| **U1 訊息序列** | `set(extractor_outputs(n)) <= set(downstream_refs(n))` for every n | 每個參數擷取節點宣告的欄位，都要被下游引用——**不能有孤兒輸出**。節點怎麼改都該成立 |
| **U3 成本／快取** | `quote["total"] == sum(menu[name]["price"] * qty ...) + service_charge(subtotal)` | 總額必須用 `menu.yaml` **重算**。這正是 `common.py` 那句「低消、服務費、菜單價格只能有一個來源」的可測版本 |
| **U7 安全邊界** | `not any(ch.isdigit() for ch in ops_resp["message"])` when `authorized is False` | 未授權的回應不得洩漏**任何一個數字**。比對字串只擋得住那一句話，這條擋得住全部 |

第三條我特別想說明：原本那句 `== "授權碼不正確..."` 只保證那一句話沒被改。
但真正該保證的是「**沒有數字外洩**」——
如果哪天有人在錯誤訊息裡加了「你已嘗試 3 次」，字串比對會紅（誤報），
而真正的洩漏（例如訊息裡不小心帶了營收數字）它抓不到。

**改寫之後，誤報消失，真正的風險被涵蓋。**

## Part A 第 2 題：系統既有的測試集算哪一種

Bistro 有 `tests/golden_set.yaml`，22 題。

### 先講做對的部分

每一題都綁一個 `failure_mode`，而且檔案開頭就寫明：

> 每一題都對應一個「已知會出事的失效模式」，不是隨便想的問句。
> 沒有對應失效模式的題目不要加 —— 題庫會愈跑愈慢，而慢到沒人跑的測試等於沒有。

**這是對的設計。** 課程講評測 harness 時要的就是這個。

### 檢查型別的分布

```
must_contain_any    22 次   ← 最多
must_not_contain    10
no_banned_phrases    5
no_compensation      4
no_invented_menu     2
must_escalate        2
```

### 我的判斷：這些不能一刀切

我原本想直接說「`must_contain_any` 是字面比對，所以是偵測器」。
逐題看過之後，這個說法不成立：

- `must_contain_any: [煙燻烏托邦]` → 比對的是**商品名**，本來就該是字面值。不是偵測器。
- `must_not_contain: [喝一點沒關係, 一杯還好]` → 禁語清單是**真的規範**，酒責法規不接受例外。這是契約。
- `must_contain_any: [煙燻, 泥煤, 油脂, 厚]`（MENU-03）→ **這個才脆弱**。它想測的是「有沒有講推薦理由」，但模型回「風味濃郁、帶點焦香」就會紅——**而那個回答是對的**。

**所以要改的不是全部，是那幾題**——字串被拿來當語意代理的那些。
判準還是同一句：把實作換掉、行為一樣，它會紅嗎？

## Part B：22 題撐得起多大的宣稱

```bash
PYTHONIOENCODING=utf-8 python course-scripts/lab5_contracts.py --ab 22 0.70 0.85
```

假設基準成功率 70%：

| 改善幅度 | 22 題分得出來嗎 | p 值 | 要幾題才夠 |
|---|---|---|---|
| +10 個百分點 | ✗ | — | 294 |
| +15 個百分點 | ✗ | 0.234 | 121 |
| +20 個百分點 | ✗ | 0.097 | 62 |
| **+25 個百分點** | **✓ 分得出來** | **0.029** | 36 |

**22 題只撐得起「25 個百分點以上」的宣稱。**

實務後果很直接：調完提示詞覺得「好像有變好」，
22 題大概率會回答「分不出來」——
**而那不代表沒變好，只代表這個量尺量不到。**

---

## Part B 的判斷：這不是缺陷，是用途被搞混

我一度想把結論寫成「題庫不夠大，要擴充到 294 題」。那是錯的。

`golden_set.yaml` 是照**已知失效模式**設計的，它問的是：

> 「這個已經修好的洞，有沒有再破？」

那是**是非題**，不是百分比。當回歸閘門用，22 題綽綽有餘——
每一題守一個具體的失效模式，全過就是全過。

而 A/B 比較問的是「版本 B 的整體表現有沒有比 A 好」，
那是**統計問題**，需要的樣本數完全不同。

**這兩件事不該共用同一套題庫。**
要做 A/B，該另外建一組隨機抽樣的題庫，而且要接受它得大一個數量級。

> 這是我這一關最主要的結論：
> 題庫沒有不好，是我一開始問錯了問題。

### 但那 15 條「看不出來」要講清楚

它們是 `is True` / `isinstance` 這類形狀斷言，
工具的 pattern 表沒涵蓋布林恆等和型別檢查。

其中有幾條其實是真契約，工具一樣看不見：

```python
assert result["metric"] == metric   # 回傳要回應輸入,這是關係
assert "rows" not in result         # 摘要不得挾帶明細
```

**這跟 Lab 3 是同一種毛病**：工具的 pattern 沒涵蓋真實程式碼的語彙。
在五關裡遇到第二次。

實際基準若更高（例如 90%），需要的樣本數會不同——
但「小改善需要大樣本」這個結論的方向不變。

因為改寫測試需要先確定「講推薦理由」該怎麼可靠地檢查，
而那可能需要一個 LLM judge——那是另一個題目。
